# Wire peripherals

Q: What's the minimum power I need to supply to a Compute Module on my own board?
A: Your motherboard must provide at least 3.3V and 1.8V power.

Q: I've got unused pins on my Compute Module. Do I need to do anything with them?
A: No, you can usually just leave unused pins disconnected.

Q: Wait, are Compute Modules actually compatible with regular laptop RAM slots?
A: Physically compatible yes, but the pinout is completely different from SODIMM memory.

# BCM283x GPIOs

Q: How many GPIO pins does the BCM283x actually have in total?
A: It has 54 total GPIO pins across three banks.

Q: I keep hearing about Bank 2 pins. Can I use those for my project?
A: Don't use Bank 2; it controls eMMC, HDMI hot plug detect, and USB boot.

Q: How do I check if my Device Tree is actually setting up GPIO pins correctly?
A: Use the pinctrl tool to check GPIO pin voltage and function.

Q: Can GPIO pins do things other than just basic input and output?
A: Yes, they can run I2C, SPI, I2S, UART, SD card, and other alternate functions.

# BCM283x boot process

Q: I'm confused about how the Pi actually boots up. What happens first?
A: The GPU DSP boots first from internal ROM, before the main ARM processors start.

Q: What file does the GPU load right at the very beginning of boot?
A: It looks for a second-stage bootloader called bootcode.bin on the boot partition.

Q: What happens if the Pi can't find bootcode.bin during startup?
A: It waits in USB boot mode for a host to provide usbbootcode.bin instead.

Q: What does start.elf actually do during boot?
A: It sets up the system, reads dt-blob.bin and config.txt, then starts the ARM processor.

# Device Tree

Q: What even is a Device Tree? Do I really need to understand it to use a Compute Module?
A: Device Tree describes attached hardware and the drivers used to communicate with it.

Q: Should I make a full custom Device Tree or is there a better way to add peripherals?
A: Use overlays instead; they add hardware descriptions without replacing the whole base tree.

Q: Where does Raspberry Pi OS look for overlay files?
A: It expects overlays in the /overlays directory with the suffix -overlay.dtb.

Q: What's the downside of using a fully custom Device Tree instead of overlays?
A: You can't use standard Raspberry Pi OS images and must rebuild it for every update.

# dt-blob.bin

Q: What exactly is dt-blob.bin and why does the GPU need it?
A: It tells the GPU how to set up GPIO pin states and GPU-controlled peripherals at boot.

Q: Do I need to create a dt-blob.bin file for my Compute Module project?
A: Not necessarily; start.elf has a built-in version if no dt-blob.bin file exists.

Q: What kind of stuff goes inside dt-blob.bin?
A: It specifies HDMI hot plug detect pin, GPCLK outputs, and the ACT LED for booting.

Q: How do I install the Device Tree compiler on my Raspberry Pi?
A: Run sudo apt install device-tree-compiler to install dtc.

Q: What command do I use to compile a dts file into dt-blob.bin?
A: Run dtc -I dts -O dtb -o dt-blob.bin followed by your dts filename.

# Arm Linux Device Tree

Q: What file does the Compute Module 3 use as its main Device Tree?
A: Compute Module 3 uses bcm2710-rpi-cm.dtb as its model-specific Device Tree file.

Q: Does the Arm Device Tree override whatever dt-blob.bin set up for the GPIO pins?
A: Yes, it overwrites dt-blob.bin pin states if they differ from its own definitions.

# Device Tree source and compilation

Q: Where can I find the source dts files if I want to look at them or modify them?
A: They're in the Raspberry Pi Linux kernel branch on GitHub; look for rpi in filenames.

Q: I want to write my own overlay. Where should I look for examples to start from?
A: Default overlay dts files in arch/arm/boot/dts/overlays are a good starting point.

# Device Tree debugging

Q: My Device Tree doesn't seem to be working right. How do I see what it actually looks like after boot?
A: Run dtc -I fs -O dts -o proc-dt.dts /proc/device-tree to dump the full assembled tree.

Q: How do I see what the GPU is logging during boot if something seems wrong?
A: Run sudo vclog --msg to dump the GPU log messages.

Q: How do I get even more diagnostic info out of the boot process?
A: Add dtdebug=1 to config.txt for more diagnostics in the output.

# Examples

Q: I just wired up an I2C RTC to my Compute Module. What GPIO pins should I use for I2C1?
A: Use GPIO44 for I2C1_SDA and GPIO45 for I2C1_SCL with pull-ups.

Q: Why should I bother setting pin states in dt-blob.bin if Linux will just reconfigure them anyway?
A: Some pins need correct states at GPU boot time before Linux drivers even load.

Q: What flag do I need when compiling a dts overlay file that has external references?
A: Use the -@ flag when compiling dts files that have external references.

Q: I want to add an ENC28J60 Ethernet controller. Do I need to write my own overlay for that?
A: No, there's already an enc28j60 overlay included in /boot/firmware/overlays.

Q: After I add the ENC28J60 overlay and reboot, how do I check it's actually working?
A: Run ifconfig to see the new eth entry, then ping 8.8.8.8 to test connectivity.

# Whole Document

Q: I'm building a custom board around a Compute Module. Where do I even start with getting peripherals working?
A: Design your board to power the module, then describe attached hardware using Device Tree overlays.

Q: What's the difference between dt-blob.bin and the regular Arm Device Tree files?
A: dt-blob.bin is GPU-specific for early boot; Arm Device Tree files describe hardware for Linux.

Q: Can I use a normal Raspberry Pi OS image if I build my own Compute Module board?
A: Yes, if you use overlays to describe your hardware rather than a fully custom Device Tree.
